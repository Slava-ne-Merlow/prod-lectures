Привет! Сегодня разберёмся, что происходит между нажатием кнопки в приложении и появлением результата на экране. Посмотрим, как общаются клиент и сервер, из чего состоит HTTP-запрос, как устроен API и как запрос попадает в нужный код. А затем запустим свой первый сервер на Python.

Начнём с устройства приложения. Допустим, ты открываешь свой профиль: в браузере или в приложении на телефоне. Интерфейсы выглядят по-разному, но имя и остальные данные пользователя должны быть одинаковыми. Откуда они берутся?

У такого приложения есть клиентская и серверная части. Клиент — программа, которая обращается к серверу. В наших примерах это сайт в браузере или мобильное приложение. Клиент показывает интерфейс и принимает действия пользователя. Когда ему нужны данные, он отправляет запрос серверу — бэкенду приложения.

Сервер принимает запрос и выполняет нужную логику. Например, находит пользователя, проверяет, какие данные можно показать, и возвращает результат. Клиент использует этот результат, чтобы обновить экран.

И сайт, и мобильное приложение могут обращаться к одному серверу. Клиент и сервер — это роли программ. Они могут работать на разных устройствах, а во время разработки — даже на одном компьютере.

Клиент и бэкенд общаются по HTTP. Это протокол, то есть общие правила обмена сообщениями. Клиент отправляет HTTP-запрос, а бэкенд возвращает HTTP-ответ. Если соединение защищено, в адресе мы увидим HTTPS.

Прежде чем разбирать конкретный пример, посмотрим на общую форму запроса. Здесь показана учебная схема: реальные значения мы подставим на следующем слайде.

В первой строке находятся метод и путь. Метод отвечает на вопрос «что сделать?». GET обычно используют, чтобы получить данные; POST — чтобы отправить данные на обработку. Путь показывает, к чему именно мы обращаемся на сервере.

Для клиента всё начинается с URL — полного адреса. Например, в нём есть схема https, адрес сервера и путь. После вопросительного знака могут идти параметры запроса: например, фильтр для списка. В записи HTTP/1.1 адрес сервера также передаётся в заголовке Host.

После первой строки идут заголовки. Они сообщают дополнительные сведения о запросе. Например, Content-Type может подсказать, в каком формате записано тело.

Затем, если нужно, передаётся тело. Это данные для сервера: например, имя пользователя при создании профиля. У некоторых запросов тела нет. Для получения профиля через GET в нашем примере оно не понадобится.

Итак, у запроса есть метод, адрес и заголовки. Тело добавляется тогда, когда серверу нужно передать данные. Теперь подставим в эту схему конкретные значения.

Допустим, пользователь открыл свой профиль. Фронт отправляет на бэкенд запрос GET /users/42. Метод GET говорит, что мы хотим получить данные, а путь указывает на пользователя с идентификатором 42. В заголовке Host указан адрес сервера — api.example.com. Это учебный адрес.

Обрати внимание: в этом GET-запросе нет тела. Для получения профиля нам достаточно указать нужный адрес.

Бэкенд обрабатывает запрос и возвращает HTTP-ответ. Код 200 OK означает, что запрос выполнен успешно. В заголовке Content-Type указан формат тела ответа — JSON. В теле находятся данные пользователя: его id и имя.

JSON — текстовый формат для передачи данных. Фронт прочитает поле name и покажет имя на экране. Если запрошенный пользователь не найден, бэкенд может ответить кодом 404.

Получилась полная цепочка: действие пользователя, запрос фронта, обработка на бэкенде, ответ и обновление интерфейса. Осталось понять, как бэкенд выбирает, какой код должен обработать запрос.

Клиент и бэкенд должны заранее договориться, как общаться. Такой договор называют API: он описывает доступные запросы и ожидаемые ответы.

Например, фронт знает, что GET /users/42 вернёт данные пользователя. При успехе придёт статус 200 и объект с id и именем. Если пользователя нет — 404. Фронту не нужно знать, как бэкенд хранит эти данные. По тому же договору может работать и мобильное приложение.

Метод уточняет, какое действие клиент просит выполнить. На примере пользователей: GET получает данные, POST обычно создаёт нового пользователя, PATCH изменяет часть данных существующего, DELETE удаляет пользователя.

Метод и путь читаем вместе. GET /users/42 просит профиль, PATCH /users/42 просит его изменить, а DELETE /users/42 — удалить. Конкретное поведение этих операций задаёт API нашего приложения. Сегодня в коде нам понадобится только GET.

В ответе бэкенд сообщает результат числовым статусом. Запомним три кода. 200 — запрос успешно выполнен. 201 — новый объект создан, например после POST. 404 — запрошенный ресурс не найден, например пользователя с таким номером нет.

Статус помогает фронту решить, что показать: данные, сообщение об успешном создании или ошибку «не найдено». Мы увидим статус 200 во время проверки нашего сервера.

У бэкенда может быть много операций. Каждой паре «метод плюс путь» соответствует свой endpoint — точка API с обработчиком. Например, GET /users/42 связан с кодом, который ищет конкретного пользователя.

Слева видно, что GET /users и POST /users имеют одинаковый путь, но разные методы. Поэтому бэкенд вызывает для них разный код. Обработчик выполняет работу и готовит ответ клиенту.

Теперь перейдём к практике: напишем бэкенд Books App на Python с FastAPI. Сначала сделаем приветствие, затем endpoint для списка книг.

Переходим в редактор. Наш проект — Books App, личный каталог книг. Сегодня сделаем основу его серверной части: два работающих endpoint. Для этого возьмём FastAPI — библиотеку для создания HTTP API на Python.

Сначала импортируем класс FastAPI. Затем вызываем его и создаём объект приложения — app. У этого приложения будем регистрировать маршруты: какой запрос каким кодом обрабатывать.

Добавим первый маршрут — ответ на GET-запрос по пути слеш, то есть по корневому пути сервера.

Строка, которая начинается с символа «собачка», — декоратор. Здесь он связывает GET-запрос по пути слеш с функцией hello. Это связь метода и пути с обработчиком, которую мы видели на слайде.

Ключевое слово def объявляет функцию. После двоеточия начинается её тело. В Python строки внутри функции пишутся с отступом — здесь четыре пробела.

Внутри у нас одна команда: return. Она возвращает словарь с ключом message и приветствием. FastAPI преобразует этот словарь в JSON, чтобы отправить его клиенту.

Мы уже описали поведение сервера. Но пока это просто код в файле. Чтобы принимать запросы, приложение нужно запустить.

Устанавливаем FastAPI с набором стандартных зависимостей. В нём есть всё, что нужно для нашего запуска. Теперь запускаем приложение командой fastapi dev и указываем файл main.py.

Открываем адрес из терминала. 127.0.0.1 — адрес нашего собственного компьютера. Имя localhost обычно используют для обращения к нему же. Число 8000 — порт: на нём наш сервер принимает соединения. А слеш в конце — путь, который мы зарегистрировали.

Сейчас браузер выступает клиентом. Мы открыли адрес, браузер отправил GET-запрос, а сервер вернул JSON с нашим приветствием.

Изменим сообщение и сохраним файл. Режим dev автоматически перезапускает приложение после изменений. Обновляем страницу — браузер отправляет новый запрос, и мы видим новый ответ.

Приветствие работает. Теперь сделаем endpoint, который относится к нашему приложению: получение списка книг.

Снова используем app.get, но путь теперь /books. Обработчик назовём get_books. Пока он возвращает пустой список: книги мы ещё не добавляли.

Обрати внимание: новая функция находится на том же уровне, что и hello. Она не вложена в первую функцию. Это отдельный обработчик для отдельного маршрута.

В адресной строке меняем путь на /books. Браузер отправляет GET-запрос. FastAPI сопоставляет метод и путь, находит наш маршрут и вызывает get_books. Результат на экране — пустой JSON-массив.

Квадратные скобки — пустой список. Сейчас мы возвращаем его прямо из кода: хранения данных у нас ещё нет. Endpoint уже работает, просто его результат пока всегда одинаковый.

По корневому пути получаем приветствие, по /books — список. Сервер один, а обработчики разные. Это и есть маршрутизация, которую мы только что разобрали на слайде.

Имя get_books нужно нашему Python-коду. Адрес для клиента задаётся в декораторе — /books. Если переименовать функцию, адрес сам по себе не изменится.

У FastAPI есть автоматическая документация. Открываем путь /docs и видим Swagger UI — интерфейс, через который удобно просматривать и проверять API.

Здесь появились обе наши операции: GET по корневому пути и GET /books. FastAPI построил эту документацию по маршрутам, которые мы описали в коде.

Выбираем GET /books, нажимаем Try it out, затем Execute. Этот интерфейс тоже выступает клиентом: отправляет настоящий HTTP-запрос нашему серверу.

Вот URL, по которому ушёл запрос, код ответа 200 и тело — пустой список. 200 означает успех. Для сравнения: 201 используют при успешном создании ресурса, а 404 означает, что ресурс не найден. Пустой список книг — это успешный результат, поэтому здесь именно 200.

Теперь мы проверили один и тот же endpoint двумя способами: через адресную строку браузера и через документацию.

Сегодня разобрались, как общаются клиент и сервер, из чего состоит HTTP-запрос и как сервер выбирает обработчик по методу и пути.

А ещё запустили собственное приложение на FastAPI. У него уже есть два endpoint: приветствие и получение списка книг. Мы отправили запросы и увидели реальные ответы.

Пока каталог пустой. В следующем видео добавим книги и научимся получать весь список и отдельную книгу по её идентификатору.
