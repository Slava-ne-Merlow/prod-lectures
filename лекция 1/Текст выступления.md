Привет! В этом уроке поговорим о клиенте и сервере: как они общаются и что происходит с запросом на бэкенде. Затем напишем небольшое приложение на Python и отправим ему первые запросы.

-----

Допустим, мы открываем свой профиль на сайте или в мобильном приложении. В обоих случаях видим одно и то же имя и другие данные аккаунта. При этом сайт и мобильное приложение — две разные программы.

Это клиенты нашего приложения. Клиент показывает интерфейс, реагирует на нажатия кнопок, а данные запрашивает у бэкенда. Например, когда мы открываем профиль, клиент просит сервер прислать информацию о пользователе.

Сервер принимает запрос, выполняет нужный код и отправляет ответ. Клиент получает данные и показывает их на экране. И сайт, и мобильное приложение могут обращаться к одному бэкенду, как на этой схеме.

Здесь под сервером мы понимаем программу, которая принимает запросы. Во время разработки она может работать прямо на нашем компьютере. Чуть позже мы такую запустим.

-----

Для общения клиента и сервера используют HTTP. Это протокол, то есть правила обмена запросами и ответами. Клиент отправляет запрос, сервер возвращает ответ.

На слайде — пример запроса на создание пользователя. Разберём метод, адрес и тело: они понадобятся нам в практике.

POST — метод запроса. Он сообщает, какое действие мы ожидаем от бэкенда. Здесь мы отправляем данные, чтобы создать пользователя.

Дальше идёт URL. Localhost означает, что мы обращаемся к своему компьютеру. Число 8000 — порт, на котором работает сервер. Путь /users указывает, к какой части приложения мы обращаемся. В данном случае — к работе с пользователями.

В Body, то есть в теле запроса, передаём данные: имя Lotty и возраст 4. Они записаны в JSON. Это формат, в котором данные можно представить парами «название поля — значение». Здесь name — название поля, а Lotty — его значение.

Тело используют не во всех запросах. Например, GET обычно отправляют без него. Чтобы запросить данные конкретного пользователя, можно указать его идентификатор в пути.

-----

Рассмотрим четыре метода на примере пользователей. GET — получить данные. POST часто используют для создания: отправляем имя и возраст нового пользователя. PATCH — изменить часть данных, например имя. DELETE — удалить пользователя.

Само слово DELETE ничего не удаляет. Для этого на бэкенде должен быть код, который выполнит удаление. То же самое с остальными методами: метод обозначает ожидаемое действие, а выполняет его обработчик.

Технически можно написать обработчик, который делает что-то другое. Но значения методов уже определены, и клиент рассчитывает на соответствующее поведение. Поэтому GET используем для получения данных, а удаление оставляем DELETE.

Метод и путь работают вместе. GET /users/42 — получить пользователя с номером 42. DELETE с тем же путём — удалить его. Путь одинаковый, а действия разные.

-----

Вернёмся к запросу с именем Lotty и возрастом 4. Допустим, сервер создал пользователя. На слайде — пример его ответа.

201 Created — статус ответа. Он сообщает, что новый объект создан.

В Body сервер вернул данные пользователя. Имя и возраст мы отправили сами, а id со значением 42 появился на сервере. Это идентификатор пользователя: по нему можно будет обратиться именно к этой записи.

Тело ответа здесь тоже записано в JSON. Клиент прочитает эти поля и, например, покажет профиль созданного пользователя. В других ответах данные могут отличаться, а иногда тела вообще нет.

-----

Код статуса сообщает клиенту, чем закончился запрос. Для начала нам понадобятся три кода.

200 OK — запрос выполнен успешно. Например, сервер нашёл пользователя и вернул его данные.

201 Created — новый объект создан. Именно такой ответ мы только что видели после создания пользователя.

404 Not Found — то, что мы запросили, не найдено. Например, мы обращаемся к пользователю с номером 999, а такого пользователя нет.

По статусу клиент понимает, как обработать ответ: показать данные, подтвердить создание или сообщить, что ничего не найдено.

-----

На сервер приходит запрос. Как понять, какую функцию вызвать? Для этого в приложении описывают маршруты: указывают метод, путь и функцию, которая будет обрабатывать такой запрос.

Точку обращения к бэкенду называют endpoint. На схеме выделен GET /users/42. Он связан с обработчиком, который находит пользователя с номером 42 и возвращает его данные.

GET /users и POST /users используют один путь, но разные методы. Для GET мы можем написать обработчик получения списка, а для POST — обработчик создания пользователя.

Вот небольшой пример на FastAPI — инструменте для создания бэкенда на Python.

Сначала импортируем FastAPI и создаём приложение. Строка app.get со слешем связывает GET-запрос по корневому пути с функцией hello. Когда придёт такой запрос, FastAPI вызовет эту функцию.

Функция возвращает словарь с приветствием. FastAPI преобразует его в JSON и отправит клиенту. Сейчас напишем такой код в редакторе и проверим его в браузере.

-----

Наш проект — Books App, каталог книг. Начнём с двух endpoint: один вернёт приветствие, второй — список книг. Пока список будет пустым. Переходим в редактор.

Для работы нам понадобится FastAPI. Устанавливаем его со стандартными зависимостями: среди них есть инструменты для запуска сервера.

Импортируем класс FastAPI и создаём объект приложения. Назовём его app. Через него будем указывать, какие запросы наше приложение умеет обрабатывать.

Добавим приветствие. Строка с собачкой называется декоратором. Здесь app.get означает, что мы обрабатываем GET-запрос, а слеш в скобках задаёт путь. Это корневой путь — без дополнительного имени после адреса сервера.

Под декоратором объявляем функцию hello. Она и будет обработчиком. При GET-запросе по этому пути FastAPI вызовет её и отправит результат клиенту.

Внутри функции возвращаем словарь: ключ message и строку Hello World. FastAPI преобразует словарь в JSON. Обратите внимание на отступ перед return: он показывает, что эта строка находится внутри функции.

Запускаем приложение командой fastapi dev и указываем наш файл. Режим dev удобен при разработке: после сохранения изменений сервер перезапускается автоматически.

Открываем адрес в браузере. 127.0.0.1 — адрес нашего компьютера, 8000 — порт сервера. В конце стоит слеш, который мы указали в декораторе.

Браузер отправил GET-запрос. FastAPI нашёл подходящий обработчик, вызвал hello и вернул JSON. На экране видим message и Hello World.

Теперь добавим получение списка книг. Метод остаётся GET, а путь меняем на /books. Функцию назовём get_books.

Пока возвращаем пустой список. Мы ещё не написали хранение и добавление книг, поэтому результат этого обработчика всегда будет одинаковым.

Меняем путь в адресной строке на /books. В ответ получаем квадратные скобки — пустой JSON-массив.

Теперь у приложения два маршрута. По слешу оно возвращает приветствие, а по /books — список книг. Какую функцию вызвать, FastAPI определяет по методу и пути запроса.

Имя функции get_books мы выбрали сами. Адрес для клиента задаёт строка /books в декораторе. Если переименовать функцию, путь от этого не изменится.

FastAPI также создаёт страницу документации. Она доступна по пути /docs. Здесь видим оба наших endpoint.

Через эту страницу можно отправлять запросы. Выбираем GET /books, нажимаем Try it out и Execute.

Ниже видим результат: код 200 и тело ответа — пустой список. Запрос выполнен успешно. Отсутствие книг не делает этот запрос ошибочным: мы попросили список и получили его, просто в нём пока нет элементов.

Проверим и первый endpoint. Здесь тоже статус 200, а в теле — наше сообщение Hello World.

У нас работает сервер на FastAPI с двумя endpoint. Один возвращает приветствие, другой — пустой список книг. Мы проверили их в браузере и через страницу документации.
