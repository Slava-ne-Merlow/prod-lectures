-----


Приложение — это программа, с помощью которой пользователь решает свои задачи: общается, делает покупки или ведёт список книг. Большинство приложений состоят из двух частей — клиента и сервера.

Клиент отвечает за непосредственное взаимодействие с пользователем: отображает данные и реагирует на его действия. Когда нужно получить или сохранить информацию, клиент отправляет запрос серверу.

Серверная часть, или бэкенд, выполняет основную логику приложения: обрабатывает запросы, работает с данными и проверяет права доступа. Результат он возвращает клиенту, а тот отображает его пользователю.

При этом клиенты могут быть разными: сайт в браузере, мобильное или настольное приложение. Все они могут обращаться к одному бэкенду и работать с общими данными.

Такое разделение позволяет разрабатывать интерфейс под каждое устройство, а общие правила обработки данных поддерживать на сервере. Клиентскую и серверную части можно развивать отдельно, согласовав, как они обмениваются запросами и ответами.


-----

Фронтенд и бэкенд зачастую разрабатывают разные люди. Чтобы работать параллельно, им нужно заранее договориться, как будут выглядеть запросы и ответы. Такую договорённость называют **контрактом API**.

API — набор правил, определяющих, какие запросы клиент может отправлять серверу и какие ответы получать.

В нём описывают, какие данные нужно передать, какие поля они содержат и что сервер вернёт в случае успеха или ошибки.

Благодаря этому фронтендер может разрабатывать интерфейс на тестовых данных, пока бэкендер реализует серверную часть. Когда всё будет готово, останется подключить клиент к серверу.

Теперь давайте подробнее разберём, как именно клиент и сервер обмениваются запросами и ответами.

-----

Клиент и сервер общаются по HTTP. Это протокол: он определяет правила отправки запросов и ответов. HTTPS использует тот же обмен, но защищает соединение шифрованием.

Давайте рассмотрим из чего состоит HTTP запрос:

Для начала остановимся на методе, адресе и теле запроса. Метод сообщает, какое действие ожидает клиент. 

URL задаёт адрес запроса. В нём есть адрес сервера и путь. Адрес сервера указывает, куда отправить запрос, а путь — к какой части приложения мы обращаемся.

При разработке сервер часто запускают на своём компьютере. Для обращения к нему используют адрес localhost. На одном компьютере может работать несколько серверов, поэтому порт помогает определить, какому из них направить запрос.

В Body, то есть в теле запроса, передаём данные. Для таких данных часто используют JSON: текстовый формат, который поддерживает объекты с полями, списки, строки, числа и другие значения. 

Тело нужно не каждому запросу. GET, например, обычно отправляют без тела.

-----


HTTP-метод определяет назначение запроса: какое действие клиент ожидает от сервера.

GET предназначен для получения данных и не должен изменять состояние сервера. 

POST передаёт данные серверу для обработки. Часто его используют для создания нового объекта, но это не единственное назначение метода.

PUT и PATCH используют для изменения данных. PUT задаёт полное новое состояние объекта, а PATCH применяет частичные изменения. 

DELETE запрашивает удаление объекта по указанному адресу.

Есть и другие методы. На них мы останавливаться не будем.

Метод и путь рассматриваем вместе. Один путь может использоваться для получения, изменения и удаления данных — с разными методами и обработчиками.


-----

После обработки запроса сервер отправляет HTTP-ответ. Давайте разберём, из чего он состоит. Пока нас интересуют две основные составляющие: статус-код и тело ответа.

Статус-код сообщает клиенту, чем закончилась обработка запроса.

Тело ответа содержит данные, которые сервер возвращает клиенту. 

Чаще всего тело ответа содержит данные в формате JSON, но иногда оно может быть пустым.

Получив ответ, клиент может использовать эти данные, например, чтобы показать информацию о новом пользователе на странице.

-----

Код статуса — число, по которому клиент определяет результат запроса. Кодов много, и они объединены в группы. Коды, начинающиеся с двойки, обозначают успех. С тройки — перенаправления и некоторые другие действия. С четвёрки — проблемы с запросом клиента, с пятёрки — ошибки на стороне сервера. Есть и информационные коды, начинающиеся с единицы.

Пока запомним три часто встречающихся статуса. 200 OK означает, что запрос выполнен успешно.

201 Created сообщает, что создан новый объект.

404 Not Found означает, что запрошенное не найдено.

Пустой результат сам по себе не означает ошибку. Если мы запросили список, а в нём пока нет записей, сервер может успешно вернуть пустой список со статусом 200. Это отличается от обращения к конкретной записи, которой не существует.

-----

Теперь посмотрим, как сервер обрабатывает запросы.

Когда запрос приходит на сервер, приложение должно определить, какой код выполнить. Для этого оно смотрит на HTTP-метод и путь запроса.

В нашем приложении каждой такой комбинации будет соответствовать функция-обработчик, которая выполняет нужное действие и подготавливает ответ.

Например, GET /users позволяет получить список пользователей, а GET /users/42 — информацию о конкретном пользователе с идентификатором 42. При этом POST /users вызывает уже другой обработчик, который создаёт нового пользователя.

Сочетание HTTP-метода и пути называют endpoint, или ручкой.

Нам не придётся самостоятельно писать механизм, который определяет нужный обработчик. Для этого мы воспользуемся FastAPI — инструментом для создания API на Python.

-----

Давайте посмотрим, как написать нашу первую ручку.

В FastAPI сначала создают объект приложения. Затем описывают функции-обработчики и указывают, на какие запросы они должны отвечать.

Для этого используется декоратор. Запись app.get задаёт метод GET, а строка в скобках — путь. При подходящем запросе FastAPI вызывает функцию под этим декоратором.

Функция может вернуть обычный Python-словарь или список. FastAPI преобразует результат в JSON и отправит клиенту. Если выполнение прошло успешно и другой статус не указан, ответ будет со статусом 200.

Остаётся запустить приложение, чтобы оно начало принимать запросы. Это и сделаем в практической части.
