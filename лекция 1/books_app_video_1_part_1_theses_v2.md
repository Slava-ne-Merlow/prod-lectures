Начнём с устройства самого приложения.

-----

Приложение помогает пользователю решать задачи: общаться, делать покупки или вести список книг.

Большинство приложений разделены на клиент и сервер.

Клиент взаимодействует с пользователем и отправляет запросы. Бэкенд обрабатывает их, работает с данными и хранит всю логику приложения.

Клиентом может быть сайт, мобильное или настольное приложение. Они могут использовать один бэкенд. Это позволяет делать разные интерфейсы, сохраняя общие данные и логику на сервере.

Чтобы эти части работали вместе, нужно заранее договориться о формате обмена данными.

-----

Эту договорённость называют контрактом API. В нём описывают запросы, передаваемые поля и ответы при успехе или ошибке.

Согласовав контракт, разработчики могут работать параллельно. Фронтендер использует тестовые данные, пока бэкендер пишет серверную часть. Затем, если контракт не нарушен, клиент просто подключают к серверу.

Теперь разберём, как устроен сам обмен: что клиент отправляет серверу и что получает в ответ.

-----

Для такого обмена используют протокол HTTP. Он определяет правила отправки запросов и ответов. HTTPS дополнительно защищает соединение шифрованием.

Начнём с запроса: рассмотрим метод, адрес и тело. Метод задаёт ожидаемое действие. URL — адрес запроса. Адрес сервера указывает, куда обратиться, а путь — к какой части приложения.

Localhost используют для обращения к своему компьютеру. Порт помогает направить запрос нужному серверу.

В Body передают данные. Часто их записывают в JSON — текстовом формате с полями, списками и значениями. Тело нужно не всегда: GET обычно отправляют без него.

Остановимся подробнее на методах: они определяют назначение запроса.

-----

Для получения данных используют GET. Он не должен изменять состояние сервера. POST передаёт данные для обработки, часто для создания объекта.

PUT задаёт полное новое состояние объекта. PATCH вносит частичные изменения. DELETE запрашивает удаление. Есть и другие методы.

Метод и путь рассматривают вместе. Один путь с разными методами может вызывать разные обработчики.

После обработки запроса сервер отправляет результат клиенту.

-----

Этот результат приходит в HTTP-ответе. В нём нас интересуют статус-код и тело.

Статус сообщает результат обработки. Тело содержит данные для клиента, часто в JSON. Иногда оно пустое. Клиент использует ответ, чтобы обновить интерфейс.

Остановимся на статус-кодах подробнее.

-----

По первой цифре кода можно определить его группу. 1xx — информационные ответы, 2xx — успех, 3xx — перенаправления, 4xx — проблемы с запросом клиента, 5xx — ошибки сервера.

200 означает успешное выполнение запроса. 201 — создание объекта. 404 — запрошенное не найдено.

Пустой список может прийти со статусом 200. Отсутствие элементов не означает ошибку запроса.

Осталось разобраться, как сервер определяет, какой код должен обработать запрос.

-----

Для этого он сопоставляет метод и путь с функцией-обработчиком. Она выполняет действие и готовит ответ. Точку обращения с определённым методом и путём называют endpoint, или ручкой.

GET /users может возвращать список пользователей, а POST /users — создавать пользователя. Выбор нужного обработчика мы поручим FastAPI.

Посмотрим, как описать такой обработчик в коде.

-----

Сначала создаём объект приложения FastAPI. Затем связываем функцию с методом и путём запроса. Декоратор app.get задаёт метод GET, а строка в скобках — путь.

FastAPI вызывает функцию, преобразует возвращённый словарь или список в JSON и отправляет ответ. При успехе по умолчанию возвращается статус 200.
